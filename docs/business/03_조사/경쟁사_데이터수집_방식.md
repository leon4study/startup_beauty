# 경쟁사 데이터 수집 방식 조사 — 합법 조달 플레이북

> 작성일: 2026-07-02
> 목적: GLOU(외국인 대상 K-뷰티, 리뷰·성분 분석 엔진 보유)가 참고할 **합법 데이터 조달 방식** 도출.
> 핵심 질문: 리뷰·소비자 인텔리전스 / 성분 스캐너 / 트렌드 분석 서비스들이 스크래핑 대신 어떤 **합법 조달 방식**으로 데이터를 확보·서비스하는가.
> 표기 규칙: [사실] = 출처로 확인됨 / [불확실] = 정황상 추정, 공식 확인 안 됨 / 비공개[추정] = 회사가 데이터 출처를 공개하지 않아 업계 통설로 추정.

## 1. 소셜·리뷰 인텔리전스 (외부 데이터를 라이선스로 사들이는 모델)

### Revuze
- **데이터 어디서**: 이커머스 리뷰·평점, 소셜 미디어, 설문(CSAT/survey), 커뮤니티/포럼, 고객 응대(CRM) 데이터를 통합. "600개 이상 글로벌 소스"(중국 포함)에서 자체 크롤러로 수집한다고 명시. [사실]
- **합법 근거**: "proprietary crawlers"로 공개 소스 수집 + 고객사 1차 데이터(설문·CRM) 결합. 공식 API 라이선스 여부는 비공개[추정]. 수집 방식이 크롤링 기반이라는 점은 공개돼 있으나 개별 플랫폼과의 라이선스 계약 유무는 공개 안 됨.
- 출처: https://www.revuze.it/social-intel/ , https://www.revuze.it/ci-hub/

### Brandwatch
- **데이터 어디서**: X(구 Twitter), Reddit, Tumblr에 대한 **공식 firehose 접근**. Facebook/Instagram은 컴플라이언트 커버리지. 2010년 이후 1.7조 개 히스토리컬 대화, 1억 개 고유 사이트. [사실]
- **합법 근거**: **공식 X 파트너**(Official X Partner)로 firehose 라이선스 보유. Reddit도 "컴플라이언트하게 최초로 firehose 접근을 제공"한다고 발표 — 즉 **플랫폼과의 공식 데이터 라이선스 계약**이 근거. [사실]
- 출처: https://www.brandwatch.com/partnerships/x/ , https://www.brandwatch.com/blog/reddit-data-announcement/ , https://partners.twitter.com/en/partners/brandwatch

### Talkwalker
- **데이터 어디서**: Twitter/X Firehose 포함 30개 이상 소셜 네트워크, 1.5억 웹 소스, 최대 5년 히스토리컬. [사실]
- **합법 근거**: X Firehose 등 플랫폼 라이선스 접근. API/라이선스 제약 하에서 TikTok·Pinterest·Reddit 커버. **공식 라이선스 구매 모델**. [사실]
- 출처: https://www.talkwalker.com/brandwatch-alternative

### Sprout Social
- **데이터 어디서**: X(공식 파트너), Facebook, Threads, Instagram, LinkedIn, Pinterest, YouTube, TikTok 애널리틱스. 각 플랫폼 공식 API 경유. [사실]
- **합법 근거**: **공식 X 파트너**(2023년 5월 전략적 파트너십 갱신 발표). X 데이터 접근 시 사용자가 X 이용약관에 동의해야 함 — 즉 **플랫폼 공식 API + 약관 준수**가 근거. 단, X API 정책 변화로 일부 X 데이터가 "network API limitations"로 제한되는 상태. [사실]
- 출처: https://investors.sproutsocial.com/news/news-details/2023/Sprout-Social-and-Twitter-Announce-Continued-Strategic-Partnership/default.aspx , https://support.sproutsocial.com/hc/en-us/articles/15529341993101-Network-API-limitations

### Meltwater
- **데이터 어디서**: 온라인 뉴스, 소셜, 웹, 채용공고, 재무공시, 제품 리뷰, 이미지 인식 등. "licensed global dataset"로 표현. [사실]
- **합법 근거**: **Reddit 공식 데이터 파트너**(Reddit Data API 경유 공개 게시물·댓글 접근). 뉴스는 라이선스 데이터셋. X는 약관상 API가 **tweet 전문이 아닌 tweet ID만** 제공하도록 제한 — 데이터 파트너 계약의 제약을 그대로 준수. [사실]
- 출처: https://www.meltwater.com/en/blog/meltwater-reddit-data-partner , https://developer.meltwater.com/docs/meltwater-api/guides/concepts/

**패턴 요약(카테고리 1)**: 소셜 인텔리전스 대형사는 대부분 **플랫폼과의 공식 데이터 라이선스(firehose/파트너십)** 를 근거로 삼는다. 과거 DataSift식 firehose 재판매 모델이 지금은 X/Reddit "Official Partner" 계약으로 대체됨. Revuze처럼 자체 크롤러 + 고객 1차 데이터를 섞는 하이브리드도 존재.

## 2. 브랜드 자사 리뷰 수집 플랫폼 (1차 데이터 소유 모델)

핵심: 브랜드가 **자기 사이트/제품 페이지에서** 후기를 직접 수집·소유하는 구조. 스크래핑이 아니라 "구매 고객에게 직접 리뷰 요청 → 브랜드가 콘텐츠 소유".

### Bazaarvoice
- **데이터 어디서**: 브랜드/리테일러 제품 페이지에서 구매 고객 대상 **자동 이메일 리뷰 요청**으로 수집(리뷰 볼륨의 최대 70%가 이메일 요청 기반). 10억 명 이상 쇼퍼 행동 데이터 + NLP + 사람 모더레이션으로 진위 검증. [사실]
- **소유 구조**: 브랜드가 자사 페이지에서 수집한 UGC를 **2,000개 이상 리테일 파트너 네트워크로 신디케이션**(같은 SKU면 Walmart/Target/Costco 페이지에 자동 노출). 즉 1차 수집 후 합법적 재배포. [사실]
- **합법 근거**: 리뷰 제출자가 "실제 제품 경험자의 진짜 의견"임에 동의, 직원·협찬·로열티 멤버 여부 공개 의무. 명확한 동의·진위 정책 기반. [사실]
- 출처: https://www.bazaarvoice.com/products/ratings-and-reviews/ , https://www.bazaarvoice.com/legal/authenticity-policy/

### PowerReviews
- **데이터 어디서**: 브랜드 자사 페이지 수집 + 1,000개 이상 리테일러 사이트 신디케이션 네트워크. [사실]
- **합법 근거**: Bazaarvoice와 동일한 1차 수집 + 신디케이션 모델.
- 출처: https://www.yotpo.com/blog/yotpo-vs-bazaarvoice-vs-powerreviews/

### Yotpo
- **데이터 어디서**: 브랜드(특히 Shopify) 자사 스토어에서 리뷰·비주얼 UGC 수집 → Google Shopping, Facebook, TikTok Shop, Target 등으로 신디케이션. Bazaarvoice 네트워크로도 신디케이션 연동. [사실]
- **합법 근거**: 브랜드 1차 데이터 소유 + 파트너 채널 배포.
- 출처: https://www.yotpo.com/blog/yotpo-vs-bazaarvoice-vs-powerreviews/ , https://www.yotpo.com/blog/yotpo-extends-its-ecommerce-marketing-platform-with-retail-syndication-on-the-bazaarvoice-network/

### Trustpilot
- **데이터 어디서**: **오픈 플랫폼** — 소비자가 자발적으로 리뷰 작성 가능하고, 기업은 자동 초대(월 50건 무료) 또는 링크 공유로 리뷰 유도. 초대·자발 리뷰 혼합. [사실]
- **소유 구조**: **리뷰는 작성한 소비자 소유** — 소비자만 편집·삭제 가능. 기업이 소유하지 않음(Bazaarvoice류와 다른 지점). [사실]
- **합법 근거**: 리뷰어 본인 동의로 생성된 UGC. 프리미엄 SaaS 수익모델(구독). 데이터 소유권이 소비자에게 있는 것이 특징. [사실]
- 출처: https://corporate.trustpilot.com/trust/how-trustpilot-works , https://help.trustpilot.com/s/article/How-does-Trustpilot-s-business-model-work

**패턴 요약(카테고리 2)**: 이들은 **스크래핑을 아예 하지 않는다**. "구매 고객 → 직접 리뷰 요청 → 진위 검증 → 소유/신디케이션"이 핵심. 데이터 소유권은 브랜드(Bazaarvoice/Yotpo) 또는 소비자(Trustpilot). GLOU가 **자체 앱 유저의 후기·반응을 직접 모으면** 이 모델의 무제한 합법 원천이 된다.

## 3. 성분·제품 스캐너 (오픈DB + 크라우드소싱 모델)

### Yuka
- **데이터 어디서**:
  - 초창기: **Open Food Facts**(위키피디아 모델의 오픈·협업 DB)에 의존. [사실]
  - 2018년 1월: 검증·모니터링 강화를 위해 **자체 DB 구축**으로 전환. [사실]
  - 현재: ① **유저 크라우드소싱**(미등록 제품은 사용자가 사진·성분 직접 입력, 다중 검증 시스템으로 정확도 확보) ② **브랜드 직접 제공**(라벨에 인쇄된 정보 그대로, 이해충돌 없음). [사실]
  - 화장품 성분: **INCI Beauty**를 데이터 소스로 활용(검색 결과 기준). [사실] (단 Yuka 공식 help 문서는 식품 위주 설명, 화장품 소스는 별도 언급 없음 — 화장품 소스는 [불확실])
- **합법 근거**: 오픈 라이선스 DB(Open Food Facts) + 유저 크라우드소싱(사용자 제공) + 브랜드 제공. **스크래핑 없이 오픈DB와 자발적 기여로 구성**. [사실]
- 출처: https://help.yuka.io/l/en/article/5a4z64amnk-how-was-the-database-created

### INCI Decoder (incidecoder.com)
- **데이터 어디서**: 화장품 포뮬레이터·과학자가 직접 작성한 리서치 기반 성분 설명. 업계 통설상 **EU CosIng**(EU 공개 화장품 성분 DB)을 기반으로 설명 가공. [사실 = 전문가 콘텐츠 / CosIng 기반은 비공개[추정]]
- **합법 근거**: 자체 저술 콘텐츠 + 공개 규제 DB(CosIng).
- 출처: https://incidecoder.com/ , https://incidecoder.com/cosdna

### CosDNA
- **데이터 어디서**: 업계 통설상 **EU CosIng** 오픈 데이터셋을 설명력 위해 가공해 사용하는 것으로 알려짐. 비공개[추정].
- 출처: https://incidecoder.com/cosdna

### skincareapi.dev
- **데이터 어디서**: **동료심사 피부과학 논문, FDA DB, EU CosIng, 기타 규제기관** 데이터를 집계. 30,000개 이상 성분, 안전등급·연구 레퍼런스 포함. INCIDecoder 방법론에서 영감. [사실]
- **합법 근거**: 공개 규제 데이터베이스(CosIng, FDA) + 공개 학술 문헌 집계. 개발자용 API로 재판매. [사실]
- 출처: https://skincareapi.dev/

**패턴 요약(카테고리 3)**: 성분 스캐너의 공통 뼈대는 **① 공개 규제 DB(EU CosIng, FDA) ② 오픈 협업 DB(Open Food/Beauty Facts) ③ 유저 바코드 스캔 크라우드소싱 ④ 브랜드 직접 제공**. 모두 스크래핑이 아닌 **오픈 라이선스·크라우드소싱·규제 공개 데이터**. GLOU SkinMatch 성분 엔진의 정석 원천.

> 참고: 지침에 언급된 **Open Beauty Facts**는 Open Food Facts의 화장품 자매 프로젝트(오픈·협업 바코드 DB)로, 화장품 성분 크라우드소싱의 대표 오픈 원천이다. [사실 — 업계 공지]

## 4. 아마존 특화 툴 (공식 API vs 스크래핑의 경계)

### Helium 10
- **데이터 어디서**: 단일 소스 아님. **Amazon 공식 SP-API**(Selling Partner API — 셀러 승인 지표: 주문·환불·PPC·수수료)를 사용하고, 그 외 추정 지표(판매량 등)는 별도 수집 결합(하이브리드). [사실 — 단 세부 수집 방식은 비공개[추정]]
- **합법 근거**: 셀러가 자기 계정을 SP-API로 인가 → 자기 데이터는 합법. 경쟁사 추정 데이터의 수집 방식(스크래핑 여부)은 비공개[추정].
- 출처: https://www.ecomcrew.com/how-to-use-amazon-seller-apis/ , https://publicityport.com/awc/5687/does-helium-scraping-amazon-both-does-this-cause-inconsistent

### Jungle Scout
- **데이터 어디서**: 2024년 자체 API 출시 — 공식 SP-API가 주지 않는 ASIN·차일드 ASIN·변형·추정 판매량 제공. [사실]
- **합법 근거**: 셀러 인가 SP-API + 자체 추정 데이터. 추정 데이터 원천은 비공개[추정].
- 출처: https://jordiob.com/amazon-tools/jungle-scout-api/

### Fakespot (경고 사례 — 반면교사)
- **사건**: 2021년 6월 Amazon이 지식재산권 분쟁을 제기, Apple이 App Store에서 Fakespot 제거(2021년 7월). [사실]
- **Amazon 논리**: Fakespot 리디자인 앱이 "Amazon 웹사이트를 앱 안에 표시하고 그 위에 Fakespot 코드·콘텐츠를 오버레이"해 **Amazon 약관 위반** + 소비자 오인 + 보안 위험 주장. 셀러 사업에 해를 끼친다는 논리. [사실]
- **결말**: 2025년 7월 Mozilla가 Fakespot 서비스 전면 종료(웹·확장 모두 2025년 8월 비활성화). [사실]
- **교훈**: 타 플랫폼(Amazon)의 콘텐츠를 **약관 위반 방식으로 래핑·재표시**하면 IP/약관 클레임 + 앱스토어 퇴출 리스크. 로그인 상태 데이터·타사 UI 오버레이는 위험. [사실]
- 출처: https://www.cnbc.com/2021/07/16/apple-removes-fakespot-from-app-store-after-amazon-complains.html , https://blog.truestar.pro/fakespot-shuts-down/

### ReviewMeta (자연 소멸 사례)
- **데이터 어디서**: Amazon 등에서 공개 리뷰 데이터를 캐싱 후 12개 통계 테스트로 분석. [사실]
- **결말**: 2024~2025년 서비스 불안정 → 2025년경 사실상 종료(사이트·확장 모두 중단). [사실]
- **교훈**: 단일 플랫폼(Amazon) 공개 리뷰 의존 모델은 지속가능성이 약함. [사실]
- 출처: https://reviewmeta.com/blog/how-it-works/ , https://tracefuse.ai/blog/reviewmeta-alternatives/

**패턴 요약(카테고리 4)**: 지속 가능한 아마존 툴은 **셀러 인가 기반 공식 SP-API**를 축으로 삼는다. 반대로 **타사 UI 래핑/약관 위반 재표시(Fakespot)** 나 **단일 플랫폼 공개 리뷰 스크래핑 의존(ReviewMeta)** 은 IP 클레임·앱스토어 퇴출·소멸로 이어졌다.

## 5. 트렌드 분석 (검색·소셜·이커머스 신호 집계 모델)

### Spate
- **데이터 어디서**: **Google Search 신호(수십억 건)** + TikTok + Instagram + Reddit 초기 신호. 검색=구매 의도, 소셜=실험·문화 확산으로 교차 검증. [사실]
- **합법 근거**: 공개 검색 트렌드 + 소셜 플랫폼 신호. 구체적 라이선스 형태는 비공개[추정].
- 출처: https://www.spate.nyc/blog/tiktok-vs-google-what-the-difference-in-search-behavior-means-for-beauty-trend-forecasting , https://www.spate.nyc/industries/beauty-personal-care

### Trendalytics
- **데이터 어디서**: **Google Trends** + 소셜 미디어 + 이커머스 판매 데이터 + 런웨이 커버리지. 자체 TikTok Insights 툴로 트렌드 속도·궤적 예측. [사실]
- 출처: https://trendalytics.co/

### WGSN
- **데이터 어디서**: 2,800개 제3자 글로벌 데이터 소스(기관·NGO·미디어) 삼각검증. 제품 예측은 5개 자체 소스(Social/Sentiment/Search/Shows/Shelf) 통합 — 소셜 월 10만+ 포스트 맵, 검색 5년+ 마켓플레이스·검색엔진 인덱스, **이커머스 shelf 데이터: 200개+ 리테일러의 3억+ SKU 매일 추적**. [사실]
- **합법 근거**: 제3자 데이터 소스 라이선스 + 자체 신호 집계. [사실]
- 출처: https://www.wgsn.com/en/what-we-do/ai-data

**패턴 요약(카테고리 5)**: 트렌드 분석은 **공개 검색 신호(Google Trends/Search) + 소셜 신호 + 이커머스 SKU/가격 데이터**를 집계하는 신호 기반 모델. 개별 리뷰 원문이 아니라 **집계 지표**를 다뤄 저작권·프라이버시 리스크가 낮다.

## 6. 데이터 판매(스크래핑 인프라)와 법적 지형

### Bright Data
- **모델**: 프록시 네트워크 + Amazon/YouTube/LinkedIn/Instagram 등 사이트별 특화 API + **사전 구축 데이터셋 마켓플레이스**로 "공개 웹 데이터"를 판매. [사실]
- 출처: https://brightdata.com/blog/web-data/best-web-scraping-apis

### Oxylabs
- **모델**: 195개국 1억+ IP, Web Scraper API/Web Unblocker/프록시, GB당 과금($9.40/GB 수준). [사실]
- 출처: https://oxylabs.io/blog/best-web-scraping-api

### Meta v. Bright Data (2024) — 핵심 판례 [사실]
- **판결(2024-01-23, N.D. Cal, Judge Edward Chen)**: Bright Data 승소(약식판결). [사실]
- **핵심 논리**: Meta 약관은 "당신의 사용(your use)"을 규율하는데, Bright Data가 **로그아웃 상태에서 공개 데이터를 스크래핑**할 때는 페북/인스타를 "사용"한 것이 아니므로 약관에 구속되지 않음. → **로그아웃 공개 데이터 스크래핑은 약관 위반이 아니며, 그 판매도 금지되지 않음**. [사실]
- **결정적 구분**: **로그인 스크래핑(계정 접근·약관 구속)** vs **로그아웃 공개 데이터 스크래핑(방문자와 동일 지위, 약관 구속 안 됨)**. [사실]
- **후속**: 판결 한 달 뒤 Meta가 청구를 자진 취하(항소 포기). [사실]
- **함의**: 로그아웃·공개 데이터 스크래핑의 법적 리스크가 크게 낮아졌으나, **로그인 뒤 접근·약관 클릭 동의 후 접근·개인정보 스크래핑은 여전히 위험**. GLOU는 이 경계를 넘지 말 것. [사실]
- 출처: https://www.fbm.com/publications/major-decision-affects-law-of-scraping-and-online-data-collection-meta-platforms-v-bright-data/ , https://techcrunch.com/2024/01/24/court-rules-in-favor-of-a-web-scraper-bright-data-which-meta-had-used-and-then-sued/ , https://brightdata.com/blog/web-data/court-rules-in-favor-of-bright-data-in-meta-v-bright-data-case

> 주의: Bright Data vs Oxylabs 특허 소송(2025~2026 Bright Data 특허 무효 확정)은 스크래핑 합법성과 무관한 별개 IP 분쟁. 혼동 금지. [사실]

**패턴 요약(카테고리 6)**: 대량 웹 데이터는 **스크래핑 벤더에서 데이터셋으로 구매**할 수 있고, 미국 판례상 **로그아웃 공개 데이터**는 상대적으로 안전지대. 단 로그인/약관동의/개인정보 선은 넘지 말 것.

## GLOU 권고 3

**권고 1 — SkinMatch(성분 엔진)는 "오픈DB + 규제 공개 DB + 크라우드소싱" 3중 스택으로.**
- Yuka·skincareapi 정석을 그대로 복제: **EU CosIng(무료 공개) + FDA + Open Beauty Facts(오픈 라이선스)** 를 기반 성분 사전으로, K-뷰티 특화 성분은 **자체 앱 유저 바코드 스캔 크라우드소싱 + 브랜드 직접 제공**으로 보강. 스크래핑 불필요. 라이선스·저작권 리스크 최소.

**권고 2 — ReactionLens(리뷰·반응 엔진)는 "자사 1차 데이터 소유" 모델을 코어로.**
- Bazaarvoice/Trustpilot처럼 **GLOU 앱 내 유저에게 직접 사용 후기·피부 반응을 요청·수집**하면 소유권이 명확한 무제한 합법 원천이 된다(카테고리 2). 이 1차 데이터가 GLOU의 해자. 외부 리뷰가 필요하면 **로그아웃 공개 데이터**(Meta v. Bright Data 안전지대)까지만, 혹은 Bright Data/Oxylabs에서 데이터셋을 **구매**해 스크래핑 주체 리스크를 아웃소싱. **Fakespot식(타 플랫폼 UI 래핑·약관 위반 재표시)·ReviewMeta식(단일 플랫폼 로그인 스크래핑 의존)은 금지** — 앱스토어 퇴출·IP 클레임·소멸 전례.

**권고 3 — 트렌드는 "집계 신호"만, 개인·약관 선은 넘지 말 것.**
- Spate/WGSN처럼 **Google Search·소셜 집계 지표·이커머스 SKU 신호**만 다루면 저작권·프라이버시 리스크가 낮다. K-뷰티 트렌드는 공개 검색·해시태그 집계로 충분. **네이버 등 로그인·약관동의 뒤 개인정보 스크래핑은 회피**(별도 메모: 여권/개인정보 인증 리스크와 결이 같음).
